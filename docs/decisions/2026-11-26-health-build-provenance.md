# 2026-11-26 健康检查报出编译来源 commit

## 背景

线上是「`git pull && npm run build` 然后重启」的自更新循环，而这个循环**没有** `set -e`。
构建失败时进程照样起来、继续服务上一次的 `dist`。于是出现一种很难看出来的故障：
进程活着、端口通、页面能开，但跑的是旧代码，功能没有生效。

更要紧的是核对方式本身不可靠——登录远端 `git log` 看到的是**已前进的 HEAD**，
恰恰会把「旧产物冒充新版本」这个要抓的场景显示成正常。要能核对，就必须让服务自己
说出「我这份产物是哪次提交编译的」。

## 范围与非目标

- 只做「报告编译来源」，不做自动纠正、不做构建失败告警、不改部署循环的失败语义。
- 不在运行时调用 git。这是本决策的核心口径，理由见下。
- 不改 `docs/architecture.md`。构建来源是运维核对信息，不是业务术语。

## 考虑过的备选

- **运行时 `git rev-parse HEAD`**：实现最省事，且不需要改构建流程。但它在构建失败、
  服务仍跑旧 `dist` 时，报的是已前进的 HEAD——正好把要查的问题掩盖掉。否决。
- **新开端点 `/api/health/build`**：已有 `/api/health` 且已受登录门卫保护（`apiNeedsAuth`
  覆盖 `/api/*`），再开一个近乎重复的健康检查，只会让「该看哪一个」变成新的歧义。否决。
- **构建期写入产物 + 并入现有 `/api/health`（采纳）**：commit 在构建那一刻落进
  `dist/build-info.json`，运行时只读文件。范围最小，语义最准。

## 最终方案与理由

`npm run build` 收尾（`tsc && rspack && node scripts/write-build-info.mjs`）把
commit、分支、是否有已跟踪文件改动、构建时刻写进 `dist/build-info.json`；`/api/health`
读该文件并在 `build` 字段返回。

这个顺序本身承载了正确性：写在 `&&` 链末尾，所以任何一步构建失败都不会执行到它，
旧的 `build-info.json` 就留在原地，如实报告**旧** commit——与仍在服务的旧 `dist` 一致。
换句话说，报告不会因为构建失败而变得乐观。

读不到文件或文件损坏时 `build` 返回 `null`，并如实表示「不知道」，绝不拿运行时 HEAD 顶替；
健康检查也不会因此 500——老产物没有这个文件是正常情况。

`dirty` 只统计已跟踪文件的改动（`--untracked-files=no`）。部署机上常年躺着
`start_service.sh`、签名包这类未跟踪的运维文件，若算进去该字段会永远为 `true`，
真正需要警惕的「产物不对应任何一个提交」就再也看不出来了。

## 遗留问题

- 构建来源只覆盖前端产物与服务端源码同处一个 `dist` 的现状；若将来前后端分开部署，
  该文件需要分别落到各自的产物里。
- 部署循环仍无 `set -e`，构建失败依旧不停服。本决策让它**可被发现**，没有让它不可能发生。
