# 2026-10-29 搜索链路时延评测与优化方向

## 背景

提问后的联网搜索流程体感太慢，用户想优化。慢没法凭印象判断——总时延由多少次 LLM 调用、
多少次联网搜索、多少次读网页、每次调用内部结构（排队/流式输出）共同决定。任何优化之前，
先要把每一跳的时延量化，否则改对了和改错了分不出来。

## 范围与非目标

- 本次只建「评测程序」并跑基准、给优化方向的先验判断；不实现任何优化方法。
- 评测对象为服务端 `runAgentTurn` 工具循环链路（LLM ↔ search ↔ read_url），不含前端渲染、
  不含断线续传逻辑。
- 不引入 LLM 自动评分（judge）——评测程序本身要能稳定跑出数才有意义，评分噪声留给后续。

## 考虑过的备选

- **只测总时延，不打逐跳**：否决。慢在哪一跳只能靠猜，无法指导优化方向、也无法区分
  「轮数变少」和「每跳变快」。
- **给每次 LLM 调用只计响应头时延**：否决。`callLlmOnce` 是流式统计正文——响应头回来得早、
  正文（流式输出）才是大头，只记头会漏掉总时延的 70% 以上，benchmark 数字会系统偏低。
- **离线 mock 上游跑评测**：否决。时延分布要贴近真实运行配置才有指导意义；mock 的时延是编的，
  结论会用不上生产力。
- **答案质量用 LLM 自动评分**：本次不做。质量护栏只记录回答字数与是否带链接来源，防止
  优化以回答变短变烂为代价；要更细的质量分数时再单独立项（采样与降噪成本高，先不背）。

## 最终方案与理由

- **打桩点选在 fetch 层**，把 `runAgentTurn` 内部所有出网调用（LLM 流式读、serper 检索、jina 读页）
  全都打时延与来源标签。理由：打桩与 runner 内部实现解耦，之后切换优化版 runner（如并行 search、
  改写 prompt 的变体）时同一套打桩能直接用。
- **时延分两段记**：headerMs（发到响应头，近似排队 + 首 token 前）与 ms（含正文消费完），
  流式正文计时用 `tapBody` 包一层 ReadableStream。理由：冒烟跑出的第一件事就是「不搜索的题
  totalMs 是 LLM 请求耗时的 3 倍多」，差了整段流式输出；不区分会导出「客服端/工具慢」的错误结论。
- **逐跳留痕进报告**：每次调用的分类、URL、headerMs、ms 以及 agent 每步轨迹都原样进
  `rawRuns`。理由：事后发现异常（如不该搜索的题被注了两次 system 消息导致两次调用）要能回查，
  不靠重跑来复盘。
- **对比以中位数聚合**：LLM 与外部接口抖动明显，中位数对单轮异常不敏感。

## 基准实测（2026-10-29，`--runs 2`，runner=current）

6 题中位总时延 **118s**；按类型分层：

| 题型 | 中位总时延 | LLM 调用 | 搜索 | 读页 |
|---|---|---|---|---|
| 不该搜索（2 题） | 14s – 47s | 1 次 | 0 | 0 |
| 该搜索（4 题） | 99s – 215s | 13 – 13.5 次 | 5 – 10.5 次 | 12 – 17 次 |

关键事实：

- **搜索题全部撞顶 12 轮工具上限**（13 次 LLM 调用 = 12 轮工具 + 1 次终答）。`TOOL_GUIDE` 的
  「宁可多查也要查全、不需要为响应速度牺牲完整性」直接驱动了轮次失控，单题搜索步数最多 24 次。
- **串行瓶颈是 LLM 轮次，不是单跳工具**。同一轮内工具调用已并发（各题工具耗时之和大于壁钟）；
  每换一个轮次，LLM 都要把越来越长的上下文重新流式输出一遍，≈30ms/字的生成速度被乘了 12 次。
- **jina 单次 p50 5.6s、p90 10.9s、max 52.8s**，与页面大小无关（接口侧渲染等待主导）；
  serper 单次约 1.7-2.5s。
- 基准期间出现过 3 次 LLM 60s 超时失败（长流式被掐断落入重试），
  这类失败会计入报告 `errors` 字段。

由此定优化优先级（按预期收益排序，待逐个实测验证）：

1. **收紧工具预算与提示词**：把「不限多查」改为「按问题类型限定搜索/读页预算」（如 search ≤3 轮、
   读页 ≤6 次），预期把搜索题从 13 轮压到 4-5 轮，是时延下降的最大来源。
2. **并行跨轮工具**：引导或合并相互独立的搜索到同一轮发起，削减 LLM 调用次数。
3. **读页更挑剔**：读页占搜索题工具时延的 2/3 以上，教会模型「摘要够用就不读」。
4. serper 结果缓存仅对重复 query 有效（学习场景重复少），缓议。

## 遗留问题

- 答案质量目前只有粗粒度护栏（字数/带链接），优化一旦压低数字，是否需要读原文评分，待第一个
  优化方案实测数据出来后再定。
- 问题集目前 6 题，覆盖面以「时延形态」为单元（不该搜索 / 该搜索 / 该搜索+读来源），
  生效后再按真实使用补代表性题。
- 逐跳留痕中未区分「这轮 LLM 是工具调用轮还是回答轮」，未来要优化话头时需要按轮次细化。
- 评测用同一台上游/同一时间段跑对比以减少日级波动的影响；跨天对比的结论只能当方向参考。

## 方法 ① 实测：search & fetch 打包为单一工具（2026-10-29，`--runs 2`）

改动：多关键词打包 search（serper 并行检索 + jina 并行抓正文，每词抓 top 2 页、每页截 3000 字、
按 URL 去重），read_url 独立工具下线，TOOL_GUIDE 引导「想清 2-4 个角度一次发出」。

结果（对比 baseline，汇总中位 **-34%**：117.9s → 78.2s）：

| 题 | 基准 | 打包 | 差值 | 机理 |
|---|---|---|---|---|
| concept-no-search | 47.0s | 31.6s | -33% | 不搜索题不受影响（差异是模型日级波动） |
| derivation-no-search | 13.8s | 13.8s | 0% | 同上 |
| recent-event | 139.6s | 36.1s | **-74%** | 模型一轮发全 1 次 search 步，LLM 2 次即可作答 |
| read-verify | 215.4s | 172.6s | -20% | 轮次 13→7，但 jina 抓取量 +60% 部分抵消收益 |
| fresh-search | 98.9s | 120.3s | +22% | 轮次 13→7 的同时 jina 跳数 16→34，抓取膨胀吃掉收益 |
| fresh-compare | 136.9s | 188.7s | **+38%** | 8 个 search 步 × 每步 2-4 词 × 每词抓 2 页 = 49 跳 jina |

关键结论：

- **轮次压缩假设成立**：搜索题 LLM 调用从 13 次降到 6-10 次，打包工具没有破坏模型行为。
- **但检索-抓取总量膨胀了**：模型并没有因为「一次能发多词」就少发 search 步（仍 6-8 步），
  反而每步词数翻倍 + 每词自动抓 2 页，jina 跳数最高到 49 次（每跳 p50 5.6s）。
- **收益兑现的条件是「模型一轮把角度想全」**（recent-event）；
  模型轮次行为不改变时，打包等于把每轮动作放大（fresh-compare）。

下一步旋纽（按预期收益排序）：

1. **收紧轮次预算**：MAX_LLM_CALLS 12 → 4-6，配合 TOOL_GUIDE 写死「每次提问最多 1-2 次 search」，
   从框架与提示两侧断掉「慢慢查」的行为通路。
2. **抓取预算封顶**：单次 search 调用抓正文总页数封顶（如 ≤4 页，按结果排名取），
   防止 query 数自动放大抓取量。
3. **每词抓取页数** 2 → 1，jina 跳数直接减半。

## 方法 ①+收口实测：轮次预算与抓取封顶（2026-10-29，`--runs 2`）

在打包工具基础上加两道闸（用户认可方案 1 与 2；方案 3 每词抓取页数 2→1 暂留，
jina 已双层并发，3 的价值在减总量而非提并发，待后续数据决定）：

- **MAX_LLM_CALLS 12 → 5**（4 轮工具 + 1 轮兜底终答，LLM 调用封顶 6 次）；
  TOOL_GUIDE 写死「每次提问最多 1-2 次 search」。
- **单次 search 抓正文总页数封顶 ≤4**（按结果排名取前）。

结果（对比 baseline，汇总中位 **-72%**：117.9s → 33.1s）：

| 题 | 基准 | 收口后 | 差值 |
|---|---|---|---|
| concept-no-search | 47.0s | 26.9s | -43%（模型日级波动） |
| derivation-no-search | 13.8s | 13.9s | +1% |
| fresh-search | 98.9s | 51.8s | -48% |
| fresh-compare | 136.9s | 39.3s | -71% |
| read-verify | 215.4s | 97.7s | -55% |
| recent-event | 139.6s | 19.1s | -86% |

关键事实：

- 搜索题 LLM 调用从 13 次压到 **3-4 次**，没有一题撞顶；
  上一轮抓取膨胀最严重的 fresh-compare 从 188.7s 回落到 39.3s。
- 搜索题总抓取跳数（serper+jina）稳定在 13-24 次，同轮并发执行，壁钟大幅压缩。
- read-verify 仍是高时延（97.7s）：题面要求「找一手资料核实」，模型用满 4 轮预算、
  单次搜索 12 跳；这轮中还有一次 jina/上游超时失败。

质量护栏：contentLen 未在评测输出中塌陷（回答篇幅随题型正常），hasLinks 正常；
注意本轮没有逐句核对，精度影响的深评估如需可单独立项。

遗留观察：read-verify 类「深度核查」需求在收紧预算下行为明显变慢于普通搜索题但仍近 100s，
是否接受此档、以及单 doc 抓取时延是否可以再优化（如压缩 PAGE_MAX_CHARS）留给后续数据决定。

## 方法 ② 实测：DeepSeek search/fetch 提供方（2026-10-31，`--runs 2`）

接入方式：`tools.mjs` 支持 DEEPSEEK_KEY 环境变量配置后整体切换——打包 search 走
`api.deepseek.com/v1/tools/search`（返回条目含 600-800 字 summary）+ `/v1/tools/fetch`（抓正文，有缓存）。
同一对外契约与输出格式。

结果（对比 capped 33.1s）：

| 方案 | 总时延 | 结论 |
|---|---|---|
| capped（serper+jina 抓正文，现有） | 33.1s | 基线 |
| deepseek 抓正文 | 42.6s | +29%，fetch 冷页比 jina 慢 2-10 倍 |
| **ds-nofetch（DS 只吃 summary 不抓正文）** | **22.5-26.5s** | **-20%~-32%，最优** |
| serper-nofetch（serper 只吃 snippet） | 32.1s | -3%，信息不足反致搜索膨胀 |

关键发现：

- **缓存没有兑现**：学习场景同一查询几乎不被重复抓取，DeepSeek 同页 2 次缓存 0.5s 的收益≈0；
  冷页 DS fetch 5-13s/页，显著慢于 jina 0.3-1.5s。
- **summary 才是核心价值**：DS search 返回的 600-800 字长摘要足以支撑作答，砍掉抓正文整块
  （fetch 5-10s/页 × 多页），这就是 ds-nofetch 收益来源。
- **质量不掉**：并排三题人工核对（诺奖/QUIC/乒乓球决赛），ds-nofetch 事实全对（含正确归因）、
  口径差异分析到位；serper-nofetch 关键事实出错（颁奖单位错写）。引用完整。

真实遗留隐患：ds 版 read-verify 里模型自称「逐段读到原文」实际只看了 summary——归因不准，
后续要加提示词约束（「引用 based on summary 而非原文」）；如有必要可加 judge 评分。

## 工具实现改进（2026-10-31）

- **fetchPages 旋钮**：`config.fetchPages` 整数覆盖（0 = 只检索不抓正文），CLI 加 `--fetch-pages` 配套。
- **评测分类从提供方改为阶段**：`serper/jina` 等旧 kind 改为 `search/fetch`，报告字段同步
  → 换提供方不再改评测代码，旧报告字段缺失时对比视图明确标住无法拆分而不是输出 NaN。
