# 2026-11-23 APP 更新改为可选，强制与否由发布时登记

## 背景

壳内启动页发现服务端有新 APK 就一律下载安装，用户没有选择权。日常迭代（样式修补、文案调整）也被当成必须立即执行的更新，手机端每次启动都可能被拦下。

## 范围与非目标

- 只管「发现新版之后怎么走」：可选更新给用户选，强制更新照旧拦下。
- 不改下载链路本身（进程内下载、SHA-256 校验、自签证书钉证、`vibe-ota-failed` 兜底全部沿用）。
- 不改 `versionName` / `versionCode` 的推导规则，也不引入第三个版本号。

## 考虑过的备选

- **按版本号大小自动判定强制**：无法表达「这版必须装」的业务判断——版本号只说明新旧，不说明兼容性。否决。
- **客户端维护兼容版本列表**：老壳读不到未来的兼容声明，且每加一版都要改客户端。否决。
- **服务端按日期强制**（如发布超过 N 天就强制）：强制时机与不兼容改动无关。否决。
- **每版发布带一个是否强制的状态**（采纳）：语义直接对应业务事实——只有存在不兼容改动的那一版才拦人。

## 最终方案与理由

发布时登记一个强制底线 `minVersionCode`，写入 `dist/app/update-policy.json`，由 `/api/app-version` 随版本信息一起下发（404 未发布 APK 时也带，缺省 0）。

- 当前 `versionCode` **低于**底线 → 强制更新：直接进下载安装流程并拦下进入应用。
- 达到或高于底线但低于已发布版本 → 可选更新：启动页给「现在更新 / 以后再说」，放着不管 5 秒后照常进入。
- 「以后再说」记在该手机本地（同一版本不再问，出现更新的版本才重新提示）。
- 底线**只升不降**，算法唯一写在 `server/app-version.mjs` 的 `nextMinVersionCode`：可选发布保持不动，强制发布抬到本版 `versionCode`，两者都不回退。底线降回去等于放不兼容的老客户端进来。

发布入口：默认可选；带不兼容改动的那一版用 `MANDATORY_UPDATE=1 bash scripts/release.sh` 发布。

## 遗留问题

- 可选更新的落地页仍是启动页，未做应用内的更新提示入口；用户不重启应用就看不到新版本。
- 这条逻辑在壳资产里，只有装了包含它的新 APK 才生效；旧壳行为不变。
