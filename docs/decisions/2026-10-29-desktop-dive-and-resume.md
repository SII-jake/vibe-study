# 2026-10-29 桌面三栏下潜布局与断线不中止生成

## 背景

移动端单栏「进入分支/返回」已验证好用，但桌面浏览器宽屏下仍用它，左右空间整片浪费；同时陆续反馈两类丢失：长回答流式生成中刷新页面或网络一抖，服务端随客户端断开中止生成，回来只能从头再问一次。

## 范围与非目标

- 本次只改桌面端布局形态与「刷新/断线后找回回答」的可靠性。
- 不动树数据模型与字段；学习数据仍只在浏览器 IndexedDB。
- 残迹不做持久层：不接 Redis、不写盘，进程重启即丢在个人自用场景可接受。
- 不改移动端交互路径；移动端继续走原单栏形态。

## 考虑过的备选

- **桌面三栏完全并列（同级全部可见）**：信息过载，追问越深越吵，视线没有主次。否决。
- **右栏弹层/抽屉**：遮挡正文，且与「顺着时间轴往下走」的心智相反。否决。
- **断线找回靠前端 IndexedDB 缓存增量**：服务端随连接中止后根本没有剩余增量，缓存什么都不是。否决。
- **残迹写 Redis**：多一个进程与配置项，只为几分钟窗口期的个人自用场景不划算。否决。

## 最终方案与理由

- **三栏下潜轨道**：左栏会话列表稳定不动；中栏是当前阅读位；追问开分支时整行内容右移，原内容退入右栏保留可见上下文，一次只让两个栏位活跃——桌面宽度用来呈现「我从哪里来」，而不是堆同级信息。
- **断开不连带中止**：客户端请求 close 不再 abort 上游生成；两个分支（agent 循环 / 纯转发）边生成边把增量写进进程内残迹仓库，TTL 默认五分钟。
- **同一份请求一个 key**：key 由消息内容与模型哈希得出，同一提问重试命中同一份残迹，天然幂等，不用额外握手协议。
- **找回走显式端点**：`POST /api/chat/resume` 按 key 返回完整文本与状态（running/done），前端不猜服务端进度。
- **SSE 解析只实现一份**：转发分支复用 agent 模块的 parser（导出后共用），不另写一套迎接 chunk 边界的代码。

## 遗留问题

- 前端尚未接线 resume：目前可靠性收益只在 API 层，刷新后自动找回需前端下次迭代接入。
- 残迹为进程内内存：服务重启或部署即丢，TTL 窗口内也失效；个人自用可接受，多人共用要重估。
- 三栏在窄桌面（接近平板宽度）的断点策略仍粗糙，按使用反馈再调。
