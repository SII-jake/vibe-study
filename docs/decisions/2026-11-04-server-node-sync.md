# 2026-11-04 对话持久化：服务端唯一事实源 + 三路合并多设备同步

## 背景

对话（问答树节点）此前只存在各设备浏览器的 IndexedDB 里（`src/storage/db.ts`），换设备、换浏览器即失联。需要服务端持久化实现多设备同步；个人自用规模，无需多用户与鉴权。

## 范围与非目标

- 管：问答树节点的服务端存取、各端防抖上传与轮询、冲突合并策略。
- 不管：多用户隔离与鉴权（单仓库开放读写，沿用既有 `/api/*` 的开放形态）；流式残迹仓库 `stream-store.mjs`（它管"断线续传"短窗口，是另一条线）；浏览器 IndexedDB 继续充当各端本地副本与离线兜底，不裁撤。

## 考虑过的备选

- **增量操作同步（OT/CRDT 式，逐条操作回放）**：节点增删、消息追加按操作序列同步，天然细粒度；但服务端要理解操作语义并维护序，个人自用规模成本远超收益，否决。
- **冲突时弹窗让用户选本地/远端**：体验最重，且个人自用几乎全是"先后写"而非"同刻写"，否决。
- **基于节点 id 的逐节点合并（最初问用户时的方案）**：可行，但用户明确拍板"像 Git 那样用 merge"，升级为带基准快照的三路合并——它能正确识别"一侧删除 vs 另一侧修改"的场景差异，纯按 id 谁新谁赢做不到。
- **浏览器 shell 调 git 命令做合并**：浏览器端无法执行，且 git 是文件行级语义、问答树是结构化数据，语义不匹配，否决；采纳的是 git 式三路合并思想在领域层重写（`src/domain/node-merge.ts`）。

## 最终方案与理由

- **服务端（唯一事实源）**：`server/node-store.mjs` 以单 JSON 文件存「version + 节点数组」快照，写临时文件再 rename 防半读；`/api/nodes` GET 读、PUT 整棵替换并带 `baseVersion` 乐观锁，版本不符返回 409 + 最新数据。个人自用规模下 JSON 文件比数据库更省事且够用。
- **前端（各端都有一份本地副本）**：`src/app/node-sync.ts` 编排三件事——`start` 对齐基准（空库且本地有数据就把本地推上去；服务端已有数据则采用服务端快照）、`watch` 本地变更防抖上传、`poll` 八秒轮询合并远端更新；`src/app/store.ts` 接入，`adoptRemote` 带基准与本端现值再并一次，保住采用瞬间的在途写入（详见 `docs/risks/frontend-risks.md` 对应条目）。
- **合并（`src/domain/node-merge.ts`）**：节点与消息两级按 id 三方对齐；一侧删一侧没动跟删、一侧删一侧改胜出；标题两侧都改取远端（服务端是汇聚点，保证各端收敛）；消息内容冲突取本地。
- **部署**：nginx `location /` 全量反代已覆盖 `/api/nodes`；数据文件默认 `server/data/learn-nodes.json`，已加 .gitignore；纯前端 + 服务端改动，远程壳无需重打 APK。

## 遗留问题

- 无鉴权：任何人拿到部署地址都能读写整棵树，仅适合私域部署；若未来暴露公网需先补访问控制。
- 基准快照只存内存：刷新后以"最新醒来的那份快照"为基准，极端情况下（两设备同时首次醒来自不同旧副本）退化为一侧覆盖，个人自用可接受。
- 服务端无数据容量上限与历史版本；树无限增长时读写均为整棵传输，届时再考虑分表或增量协议。
