# 2026-11-26 同一会话多条追问 lane 并发生成

## 背景

生成状态原来按会话建键：一条回答在跑，整个会话就被锁住。后果是主线生成期间发起追问被静默拒绝，
而追问分支的输入框反而显示停止按钮、按下去停掉的是主线那条。追问在数据上本来就是各自独立的分支，
它们之间没有先后依赖，没有任何理由互相阻塞。

## 范围与非目标

- 只改"生成状态按什么粒度记账"，从而让不同追问分支能同时跑。不改生成协议、不改消息结构、不改同步。
- 同一 lane 内仍然互斥：同一条回答不能同时跑两份流。
- 版本切换（`selectVersion`）仍保守地按会话挡住。它只拿得到 messageId，无法廉价判定该消息属于哪条 lane；
  放开需要另做归属查询，不在本次范围。
- 不改 `docs/architecture.md`。lane 是存储键的粒度概念，不是新增业务术语。

## 考虑过的备选

- **维持按会话加锁**：实现最省事，但追问互斥是纯粹的伪限制，用户能同时问两个方向本就是产品价值所在，否决。
- **按消息 id 建键**：粒度太细，同一条回复的重试与主流程会各建一把锁，反而挡不住并发写同一份回复，否决。
- **按 lane 根建键（采纳）**：lane 根天然对应"一条独立对话线"，同 lane 内的重复生成正好该被挡住，
  跨 lane 正好该放开。判定、停止、落盘、缓存淘汰、删会话、换历史统一切成这个粒度。

## 最终方案与理由

`streamKeyOf(sessionId, laneRootId)` 成为生成状态的唯一键：主线 lane 仍用会话 id（保持既有落盘与缓存口径不变），
追问 lane 追加 lane 根 id。界面层的停止按钮、发送按钮、各 lane 正文状态都按这个键取，不再看会话级布尔。
落盘按会话去重（同一会话可能有多条 lane 同时在跑），避免一次保存写多遍。

## 遗留问题

- 版本切换的会话级保守锁：放开需先解决"由 messageId 反查所属 lane"的开销问题。
- 静默拒绝的旧交互已取消，但没有任何提示告诉用户"这条 lane 正在生成、请稍等"——提示文案待产品定。
