# 一键发布脚本 release.sh

## 背景

发布动作此前分散在多处：手动 `npm run build`、手动 `scripts/publish-apk.sh`、手动杀进程重启 node 后端。人的诉求是「我说发布，代理就直接执行一个脚本完成：打包 APK + 重启前后端」。

## 范围与非目标

- 发布=让线上（127.0.0.1:8787，nginx 反代到外部域名）跑起当前 checkout 的代码：前端 `dist/` 重新构建、APK 重新打包落到 `dist/app/`、后端进程重启。
- 不做 versionName 自动 bump（发版决策属人，AGENTS.md 版本纪律节已定）。
- 不做 git push/merge；git 动作走各自授权。

## 考虑过的备选

1. 每个动作保留独立脚本，代理按话术依序执行：步骤间的中间态失败（如 build 挂了但进程已被杀）要代理每次现场编处理逻辑，不可靠。
2. 重启按端口 `pkill`/`fuser -k`：同机可能跑其它项目的服务，按端口杀属于不可接受的误伤面。
3. systemd/pm2 接管：引入尚未评审的运行时依赖，部署架构变化要走 architecture.md 评审，超出本批范围。

## 最终方案与理由

单一 `scripts/release.sh`，六步链条：单测质量门 → 前端构建（`dist/`）→ 打包 APK（复用 `publish-apk.sh` 的构建+验签+落盘）→ 产物与 build.gradle versionName 对拍 → 重启后端 → 健康检查。

关键取舍：

- **重启的安全红线**：只允许杀「监听 8787 ∧ cwd=本仓库 ∧ 命令行为 `node server/index.mjs`」三者全中的进程；端口被占但身份不匹配时宁可中止发布报错，绝不猜。停机先 TERM 等 10s 再 KILL。
- **新进程脱离脚本存活**：`setsid nohup` 起新后端，日志沿用 `/tmp/study-api.log`（与人工起服务的既有习惯一致）。
- **健康检查认服务端唯一口径**：轮询 `/api/app-version`（服务端扫 `dist/app/` APK 文件名的口径与 build.gradle 对拍），加静态首页可达，全过才算发布成功；失败打出日志末尾并中止。
- **「重启前端」没有独立对象**：生产上唯一的 node 进程同时服务 API 与 `dist/` 静态产物，重启后端 + 重新 build 即覆盖前后端，不为「前端」虚构第二个进程。

## 遗留问题

- 发布窗口内（旧进程死到新进程健康，通常几秒到十几秒）服务不可用；目前单用户自用可接受，真要零停机需双进程/端口切换，属部署架构议题。
- `/tmp/study-api.log` 只追加不轮转，长期跑会无限增大；量小，暂由人工处理。
