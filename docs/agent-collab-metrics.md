# 人机协作度量

本文件登记 AI 代理协作过程中的坑与返工事件，以及定期回顾时的汇总口径。
制定协作规范是为了少踩坑；本文件回答"规范到底有没有起作用"。

## 为什么记

- `docs/risks/` 记的是技术坑长什么样；本文件记的是**协作过程**哪里断的（规格不清没人问、静默跳过检查、带病开工）。
- 只有登记下来，才能分得清某条铁律是"一直在起作用所以没人违反"，还是"写了但没人执行"。

## 三个观察指标

1. **事件数**：本次回顾周期内登记的坑/返工事件条数。目标不是压成零（报不出来比有坑更糟），而是看趋势与重复率。
2. **一次通过率**：agent 交付第一次提交即通过 review、无返工的比例。低说明任务规格或自检环节有问题。
3. **遗漏缺陷**：合并后才暴露、本应在 checklist 或测试环节拦下的缺陷数。凡出现必查是哪个环节漏的。

## 什么事件要登记

满足任一条件就记一条：

- 实际发生了返工（review 打回、合并后 hotfix、推倒重做）。
- 违反了铁律或 checklist 条文，无论是否造成后果（含被自检拦截的未遂事件）。
- 发生了"上面分类里没有"的新型坑——这类必须记，它是规范进化的唯一输入源。

纯技术坑（某库用法踩雷、某 API 行为反直觉）仍按原渠道进 `docs/risks/`；只有当坑的根源是协作过程问题（规格、边界、跳过、隐瞒）时才登记到本文件。

## 事件分类

| 分类 | 含义 | 对应的防线 |
|---|---|---|
| 规格不清 | 需求模糊时代理自行开干、猜错返工 | 人类权威边界：问人条款 |
| 未升级判断 | 涉及业务语义/对外动作时代理单方面决定，被纠正 | 人类权威边界 |
| 静默跳过 | checklist 项勾不出来但 PR 里未报告 | 铁律 7 验收 |
| 带病开工 | 冷启动自检未过仍继续改代码，后续整批返工 | 冷启动自检 |
| 术语/契约漂移 | 同义改写、字段改名绕过 architecture.md | 铁律 2 + 守护检查 |
| 越过门禁 | 未等人发话即自行建 PR、零散 commit 逐个 push | 铁律 8 子律 |
| 其他 | 以上都不覆盖的事件，必记 | — |

## 记录格式

新事件加在下方"事件登记"小节的最上方，每条一行：

```
- YYYY-MM-DD | 分类 | 一句话事件描述 | 根因一句话 | 导致的规范/检查变更（或"无"）
```

示例（格式示例，非真实事件）：

```
- 2026-01-15 | 静默跳过 | PR 未报告测试未跑就提交 | 清单只要求"过一遍"没要求报告状态 | 铁律 7 增加显式报告验收
```

## 回顾节奏

- 每个发布周期（或最长一个月）回顾一次，按上表三个指标汇总。
- 同一分类反复出现 ≥3 次：对应防线条文不够硬或没有可执行检查，升级 AGENTS.md / checklist。
- 连续两个周期零登记：优先怀疑"漏报"而不是"没坑"，抽查两个 PR 的 checklist 执行痕迹。
